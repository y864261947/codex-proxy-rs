# 来源路由实施设计

状态：第二批开发中的实现约束；对外产品范围见 `navigation-and-scope-proposal.md`。

## 独立身份

- `ProviderKind` 继续表示编译进二进制的适配器。现有 `openai`、`xai` 账号适配器保持原身份；官方 API/第三方渠道使用对应协议适配器，不能把供应商名当成具体渠道 ID。
- 外部渠道使用 `ChannelId`；自建号池使用已有 `AccountGroupId`。实际账号始终使用原 `ProviderAccountId`，渠道不创建虚构账号行。
- 模型供应商是目录和监控分类属性，与渠道名称及客户端/上游协议分别存储。OpenAI 兼容协议并不代表模型由 OpenAI 提供。
- 多个渠道如果共享同一上游项目配额，可明确关联 `QuotaScopeId`。渠道改名、复制或被多个下游组使用不会复制实际配额。

## 选择与占用

接入分组先限制模型与允许来源，之后按能力、启停、健康、容量过滤，按优先级及同级权重选择。号池选定后继续使用已有池内账号选择。每次尝试冻结实际来源；账号可属于多个号池，但本次只能归属选中的一个号池，并继续占用账号全局槽位。

候选和调用结果必须同时确认适配器、模型、具体来源及实际凭据身份。已有 Coordinator 的发送/交付屏障保留；已经向下游交付后的生成不自动重放。历史记录保存来源 ID 与名称快照，改名、删配置不重写历史。

来源容量在上游尝试期间持有；下游的全站/客户/组/Key 容量按逻辑请求持有。来源获取失败不留下部分占用。内部测试和探针仍消耗真实来源/账号容量，但使用独立预算和统计标记。

会话续接必须保持原具体来源与凭据身份，不能仅凭相同供应商名切到另一个渠道。无法确认继续执行位置时保留不可续接/待核对状态，遵守已有安全重试条件。

号池来源计划按较小优先级值优先，同级按权重生成请求内固定、无重复的尝试顺序。每个池的账号范围与认证范围求交，Provider 只收到该候选的范围。原生响应亲和同时冻结号池；Provider 证明可安全恢复时可在原池内换号，但不能借此切换号池。旧亲和记录仍按账号权限检查，成功后写入新来源绑定。

## 兼容边界

旧 Key 的账号范围继续生效，不因添加渠道自动获得新渠道权限。接入分组的来源集合采用显式允许；空集合拒绝。现有账号列表、凭据刷新和账号调度继续由各自 Provider 拥有。

渠道公共配置与凭据分开：Admin 管名称、启停、限额、来源关系和安全审计；Provider 解析凭据与协议、发现可用模型并执行请求；Store 负责持久化和协调。目录与列表不能返回完整凭据，URL 不接受内嵌凭据或查询参数密钥。

渠道持久化保存 Provider 校验后的不透明配置对象，Core 和 Store 不解析其认证字段。普通管理列表不选择该列，Provider 使用独立端口读取启用渠道；更新要求当前渠道版本，配置变更和安全审计原子提交。候选最终调用时携带冻结版本，版本已变化就重新规划或拒绝，不能使用新凭据冒充旧候选。公共配置编辑也推进版本，避免旧管理表单覆盖已轮换的配置。

## 接续步骤

1. 建立稳定渠道/共享配额身份和调用目标契约，为现有账号路径补充回归测试。
2. 实现渠道配置、凭据更新、事务审计和运行快照；接通一个文本协议的完整调用与失败路径。
3. 扩展来源优先级、同级权重、号池/渠道/共享配额容量，以及请求历史来源维度。
4. 模型目录、发现、价格和测试记录进入第三批；逐厂商协议及媒体能力按第五批逐项验证，目录不提前标记为可调用。

本文件描述实施目标，不代表上述渠道功能已经交付；实际状态以实施记录和 CI 为准。

## 首个 API 适配边界

先在现有 OpenAI Provider crate 内增加独立的 API 渠道适配器，复用该 owner 的 Responses 协议解析；使用独立的 ProviderKind 与 API Key 认证，不进入 Codex OAuth 账号选择。当前网关客户端入口是 Responses；Chat Completions、Anthropic、Gemini 的转换按后续协议批次分别验证。

2026-09-10 核对官方资料：[模型列表](https://developers.openai.com/api/reference/resources/models/methods/list) 返回模型 ID、归属和生命周期等基本信息，不能据此推断价格或完整能力；[流式响应](https://developers.openai.com/api/docs/guides/streaming-responses) 使用 SSE 及具名生命周期事件。初始 API 渠道显式配置 Responses 模型集合，自动发现与能力确认在第三批处理。

首个实现按具体渠道版本读取配置，HTTP Client 禁止重定向；凭据仅来自渠道，不传递下游认证或 Codex OAuth 画像。Provider 在 Core 已记录 attempt 后首次 poll 才发送一次请求，收到响应头前的取消按发送不确定处理，收到头后的截断按已发送处理。客户端 JSON/SSE/WS 仍由现有 API 适配层消费同一 Responses 流。

该阶段 API 渠道保留 usage 而不沿用 OAuth 模型估算价，价格必须由后续价格版本明确归属。原生 previous-response/conversation 尚无渠道级续接 owner，暂时拒绝；`background: true` 也必须等待异步任务租约实现，不能返回排队状态后提前释放逻辑容量。
