# 渠道与自建号池监控建议

日期：2026-09-10。状态：需求讨论稿；本轮不创建实际探针、发起模型调用或修改线上配置。

关联：[菜单与范围](navigation-and-scope-proposal.md)、[候选清单 H01–H05](feature-integration-candidates.md)、[模型管理](model-management-candidates.md)。

## 已确认需求与建议边界

用户关心自定义名称的上游渠道和自建号池的健康度，要求可配置探针，观察成功率、首字延迟、缓存率，并按模型供应商分类。

建议增加一级菜单“监控中心”，以供应商为默认分组维度。频率、阈值、通知方式、保留周期和自动处理策略仍是建议，尚未由用户确定。当前只讨论内部监控，不默认建设公开状态站。

## 监控对象与分类

- **模型供应商**：OpenAI、Anthropic、Google Gemini、xAI/Grok、DeepSeek 等。分类依据模型目录的供应商信息，不能根据所使用的兼容协议判断。来源不明时显示“未知/自定义”。
- **接入来源**：官方渠道、第三方渠道、自建号池中的账号分组。使用管理员命名，底层保持稳定 ID；改名不丢失历史。
- **具体目标**：供应商 + 来源 + 上游模型 + 协议/能力 + 测试配置。号池观测还可下钻到账号。
- 同一个第三方渠道可提供多家模型，在每家供应商视图下显示各自的切片，实际渠道配置只有一份。
- 若把实际 A、B 两个上游归到同一个显示名称下，建议用可展开的来源集合视图；必须保留成员结果，不能只剩一个合并成功率。此集合不是新的下游授权分组。

默认浏览方式：

```text
监控中心
  供应商筛选：全部 / OpenAI / Anthropic / Gemini / xAI / DeepSeek
  页面标签：渠道与号池 / 探针任务 / 告警记录
  来源列表 → 模型详情 → 账号明细（自建号池）
```

渠道与号池列表在同一供应商内并排比较；支持来源类型、模型、能力、时间范围和状态筛选。详情链接到来源配置、模型测试记录和脱敏请求日志。

## 首页与全站指标

首页展示全站摘要，监控中心提供渠道、号池、模型、客户/Key 等细分与长时间窗口分析。两者复用指标定义与数据，不维护互相矛盾的计数器。

| 指标 | 建议计数口径 |
| --- | --- |
| 当前运行请求 | 已准入且尚未结束的下游业务逻辑请求；SSE 持续到终态，WebSocket 统计活跃生成而非空闲连接。等待队列单列，同一逻辑请求的来源重试不重复计数。 |
| 业务入站 RPM | 最近滚动 60 秒到达所定义模型业务入口的逻辑请求数；分别显示已准入和拒绝数。管理员接口、健康检查和媒体状态轮询不混入模型调用量，人工测试/探针单列。 |
| 上游调用 RPM | 同窗口实际发送的来源尝试数；一次下游请求的多次重试分别计数，用于解释额外上游负载。与业务入站 RPM 分开。 |
| 来源并发占用 | 渠道、号池、实际账号的当前执行占用与各自上限。按实际资源 ID 和配额范围聚合，重叠账号组不能叠加容量；不把下游与上游各层占用重复相加。 |
| 等待与拒绝 | 当前等待数、等待耗时分布、窗口内因客户/Key/组限额拒绝与因来源满载拒绝的数量。 |
| 未完成媒体任务 | 已接收而尚未确认终态的图片/视频任务；排队、运行、待核对分别展示，不因提交接口返回或本地停止轮询而清零。 |
| TPM | 窗口内已观测的输入/输出 Token，明确以用量上报时间还是完成时间归桶；流式累计用量需去重。缺失用量保留未知，不将其当成零或声称精确测得生成中的 Token 速度。 |

首页默认最近 60 秒 RPM，不用今日总请求除以分钟数代替。不同时间窗口的成功率、延迟、成本各自标注，零样本不能显示 100% 成功。全站当前运行数与上游理论容量是不同指标，没有全局硬上限时不显示虚构的“当前 / 全站上限”。

建议首页展示运行数、RPM、等待数、媒体任务，附服务表现、供应商摘要和今日统计；详细分层占用仍在监控中心。实时摘要可采用约 5 秒刷新，记录采集与刷新时间。当前部署为单实例；未来若扩展多副本，须明确集群范围、去重与数据新鲜度后才标注为全站聚合。

## 同屏展示两类证据

| 证据 | 解决的问题 | 展示方式 |
| --- | --- | --- |
| 真实请求 | 用户实际调用是否稳定、是否变慢、缓存使用如何 | 成功率、延迟分布、缓存率、请求量、错误类型；默认作为运营统计 |
| 主动探针 | 无流量时能否调用；指定来源和能力是否可用 | 最近结果、探针成功率、首字/完成耗时、时间线、最近成功时间 |

探针、管理员手动测试和用户真实请求分别标记。探针用量计入独立运维成本，不混入客户额度或真实流量指标。第三方产生的实际费用仍需记录，未知费用不能当成零。

每张卡片显示时间窗口、样本数、数据更新时间和覆盖范围。没有流量、没有运行探针、暂停、数据过期与已知故障分别展示，不能全部用绿色“正常”表示。

## 指标口径

| 指标 | 建议定义与展示 |
| --- | --- |
| 下游请求成功率 | 按一次逻辑请求计数，使用明确的终态分类；显示成功、服务失败、调用方错误、取消和未完成数量。服务成功率采用成功 /（成功 + 服务失败）；不隐藏被排除的数量。 |
| 来源调用成功率 | 每次实际上游尝试独立计数；A 失败后 B 成功，A 仍保留失败，B 保留成功，下游逻辑请求只记录一次最终结果。 |
| 探针成功率 | 通过验证的完成探针 /（通过 + 失败）；跳过、预算暂停、执行器未运行等单列。真正发出后超时属于失败或待核实结果，不能写成跳过。 |
| 首个输出与首字延迟 | 分别保存可见输出、正文文本以及已可观测的推理/工具事件时间；图表明确选择了哪种口径。响应头、心跳和空 SSE 事件不当成首字。 |
| 延迟范围 | 区分网关收到请求至下游首个正文输出，与网关发往某来源至该来源首个正文输出。前者包含排队/重试等网关路径，均不声称测得用户设备网络时间。展示 P50/P95 与样本数。 |
| 请求缓存命中率 | 缓存读取 Token 大于零的请求数 / 有有效缓存用量报告的请求数；同时显示报告覆盖率，不能把未返回数据的请求当成未命中。 |
| 缓存 Token 占比 | 同一有效样本集合的缓存读取 Token 总量 / 归一化后的输入 Token 总量。缓存写入单列；不是逐请求百分比的简单平均。 |
| 容量与失败 | 并发占用、排队、429、超时、授权失效和上游错误分开。区分下游 Key 不合法与配置给上游的凭据失效，后者属于来源异常。 |

成功必须依据协议终态与响应有效性判定；HTTP 200 后流式中断不能计为完整成功。合规的拒答、工具调用等按各自语义记录，不能因未出现普通正文就一律判为渠道故障。

供应商或来源集合的成功率从计数聚合，延迟分位数从样本或可合并分布计算，不能平均子项成功率或 P95。并排比较时固定模型、协议、测试模板和服务档位，注明输入长度、缓存与流量构成差异。

## 缓存监控的边界

缓存率描述缓存使用情况，不直接证明服务健康。真实请求内容、会话路由、缓存条件和上游报告方式均会影响读数。缓存率下降可触发优化提示，但默认不因此摘除渠道。

按供应商实现用量归一化，保存原始字段与归一化版本。例如 Anthropic 文档将总输入 Token 定义为普通输入、缓存读取和缓存写入三者之和；不能把原始 `input_tokens` 一律当作总输入。数据异常显示原因，不通过截断到 100% 掩盖错误。

缓存能力探针单独执行“首次请求 + 保持前缀/凭据范围等条件的重复请求”，使用满足目标模型要求的模板。普通短问候不保证触发缓存。探针的缓存读数与真实请求的缓存率分开，上游报告不能作为对第三方内部实现的独立证明。

## 探针配置

从渠道、号池或模型详情点击“添加监控”，预填来源及模型；监控中心统一管理任务。

人工试用与多模态效果验证在“模型管理 → 测试工作台”进行，详见 [模型测试体验](model-management-candidates.md)。可以将测试模板带入探针配置，但需单独设置周期、预算并启用；两者复用执行适配和产物任务，运行类型与统计分别记录。

建议可配置字段：名称、来源、模型、协议/能力、模板、周期、超时、最大输出、运行时段、并发限制、调用预算，以及失败/恢复阈值。

- 轻量文本探针可提供每 5 分钟的起始模板，用户保存启用后才运行；不自动对所有模型和所有账号生成任务。
- 探针固定目标来源，失败后不能切到别的渠道再将原渠道标绿。若配置重试，保存每次尝试及重试后恢复状态。
- 普通可用性探针使用合成内容。需要测非缓存表现时设置适配的独立模板，并按实际返回的缓存信息标注，不能假定加随机串就一定完全冷缓存。
- 使用与生产对应的网络出口和适配路径，记录探针位置。服务器内探针只证明该位置到目标的路径，不能代表全部用户或公网入口都可用。
- 任务错峰、限制并发；执行器重启后避免重复执行和补发大量过期任务。执行器心跳中断应标注监控数据失效。
- 保存前预览每日调用规模：实际配置目标数 × 每日运行次数 × 每次请求数。20 个目标每 5 分钟一次，即至少 5,760 次请求/天，尚未计重试和缓存成对测试。
- 定时任务需要可关闭、可暂停；达到调用预算暂停并显示原因。费用无法可靠估算时，以次数及 Token 上限约束。

## 自建号池的专属视图

除通用请求指标外，展示总账号、可调度账号、限流/冷却账号、授权失效账号、额度与重置时间、并发占用及最近巡检时间。

并发占用按渠道、号池、实际账号、接入分组、客户和 Key 分层展示“使用中 / 上限”，关联排队与阻塞原因。图片/视频增加未完成任务占用；共享账号不重复计算物理容量。已满载但调用正常的来源显示容量状态，不因此判为故障，规则见 [并发限制与调度建议](navigation-and-scope-proposal.md)。

额度按同一供应商、套餐和配额窗口展示，不把不同模型权限或不同计量单位的剩余额度直接加总；可调度账号数按所选模型计算。

探针分为两种覆盖：

- **号池调用探针**：经过该池正常的账号调度，验证至少有一条当前可用调用路径，记录最终账号。
- **账号轮巡**：分批指定账号探测，记录已测账号数/待测账号数、时间及结果；可结合授权状态和配额接口检查。不会因池内一个账号成功，就宣称所有账号健康。

某模型不可用时记录在对应来源、模型和能力下；只有有足够共同原因的证据时才上升为整个账号、渠道或供应商的故障。

## 图片与视频

文本模型显示首字时间；图片/视频生成显示提交耗时、排队时间（能观测时）、总完成时间、终态成功率和结果可访问性。上游未暴露的阶段时长显示未知，不用首字指标替代。

生成类探针独立配置频率与预算。视频创建任务返回成功只代表提交成功，需关联后续轮询到终态；任务提交结果不明时先查询/核对，不能盲目重建任务。

## 状态、告警与路由联动

- 健康状态建议采用“正常 / 性能下降 / 不可用 / 未知”；暂停与维护单列，并显示证据来自探针还是实际请求。
- 阈值按供应商、模型和能力配置。起始模板可用连续 3 次失败触发、连续 2 次成功恢复；它只是待调参数，不是已确定的服务承诺。
- 成功率/延迟告警须满足最少样本或持续窗口，避免一次低流量样本触发大范围故障判断。缓存告警主要用于变化提示。
- 站内事件、通知通道、去重、冷却、维护静默及恢复通知复用同一事件模型；同一故障持续期间不重复轰炸。
- 可选自动隔离先作用于具体来源/模型并保留原因，配置恢复试探与冷却；人工停用不能被探针自动恢复覆盖。
- 路由联动是单独启用的策略，不能仅因建立监控就擅自改优先级、跨接入分组切换或恢复人工禁用来源。

## 控制复杂度与实施顺序

当前代码已有成功/失败分类、首字与阶段耗时、缓存 Token、账号用量等基础，优先复用现有采集与聚合能力。后续补齐来源尝试、供应商/模型维度和探针标记，不建立第二套互不一致的日志或计费系统。

1. 在完整调用链建设时预留稳定来源 ID、模型供应商与请求来源类型，保留逻辑请求和上游尝试的关联。
2. 第一阶段提供供应商分类的渠道/号池看板、真实流量指标、定时文本探针和站内异常记录。
3. 后续增加账号轮巡、缓存专项探针、通知通道，再扩展图片/视频终态探测和可选路由联动。

初期利用现有数据库与后台任务机制，采用有界查询、聚合和保留周期；避免对每次看板刷新全量扫描历史。若需要历史回填，渐进执行并显示覆盖进度。暂不引入独立时序集群或把外部监控工具作为使用前提。
